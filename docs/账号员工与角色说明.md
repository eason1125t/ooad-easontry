# 账号、用户、员工身份与角色的安排

日期：2026-10-21。适用于当前 RBAC0 本机版本，已对照实际表结构及三个演示账号核验。

## 概念

账号承载系统用户身份，员工保存人员资料，角色决定账号能做什么。“用户”目前是业务称呼，没有另建 user 表；界面统一称“账号角色分配”，数据库关联表仍叫 user_role。

| 概念 | 含义及数据 |
| --- | --- |
| 账号 account | 登录和授权主体，包含用户名、显示名称、启用/锁定状态、可选员工关联；密码 BCrypt 哈希单独存 credential |
| 用户 | 使用系统的人；本版本授权流程中的“用户”就是账号，不是独立持久化实体 |
| 员工 employee | 公司人员资料，包含组织、岗位等；人员存在不等于具备登录能力 |
| 角色 role | 一组明确操作权限；名称用于展示，稳定编码用于识别，没有角色名绕过 |

## 关系与基数

账号与员工双方均为 0..1：员工可以没有账号，账号也可以不关联员工；account.employee_id 可空且唯一。该约束不等于系统已识别所有自然人的唯一身份，无员工账号仍由管理人员负责核实用途。

账号与角色多对多（user_role），角色与操作权限多对多（role_permission）。账号最终权限是所有有效角色提供的有效操作权限并集，重复权限只算一次。目前没有角色继承、互斥或部门自动授权。

员工属于组织，可以有岗位；组织层级、岗位名称及原始 Excel 模板均不自动产生角色或权限。操作权限属于具体功能点，资源目录按应用、模块、功能点分层。

## 当前三个账号

| 账号 | 员工关联 | 角色 | 登录行为及权限 |
| --- | --- | --- | --- |
| project_admin | 无 | 平台管理角色 platform-admin | 可选管理或员工入口；当前显式授予 13 项权限 |
| demo_user | 合成的“演示员工”，ID 1 | 文档阅读角色 demo-reader | 自动进入员工演示；可读两条合成文档 |
| flow_user | 无 | 流程演练阅读角色 A，flow-reader-a | 自动进入员工演示；仅有 demo.documents:read |

界面验收角色 ui-review、流程演练阅读角色 B（flow-reader-b）目前未分配给上述账号，且没有权限。它们保留作为可复查的合成测试对象。

数据库共有 10,001 条员工资料：10,000 条来自原始文件，1 条为合成员工。原始员工没有自动生成登录账号，当前只有合成员工关联 demo_user。管理员及 flow_user 的员工资料为空，员工入口显示明确空态。

密码以用户最新指定及 .local/测试账号.md 为准，不把聊天中的旧密码视为当前配置。

## 管理员与员工入口

管理员是一种授权结果，员工是一种人员身份，二者可以同时成立。一名员工关联的账号可以获得管理角色；管理员账号也可以没有员工关联。

有效权限含 platform:access 才能进入管理入口选择；每个管理 API 仍需对应具体权限。用户名或角色名称里出现 admin 不会绕过鉴权。最后完整管理员保护要求至少保留一个启用、未锁定且拥有全部必要管理权限的账号。

员工演示入口是页面名称，不要求账号已绑定 employee。无员工关联的外部或测试账号同样可以进入该页，并按实际权限执行操作。当前合成文档不代表已实现“本人/本部门”的生产数据范围。

## 会话与实时授权

会话识别账号，不固定一份旧角色权限快照。后端每次重新计算有效权限，授权回收提交后，后续开始鉴权的请求立即使用新状态；已通过鉴权的在途请求允许完成。账号、角色、权限或资源祖先停用都会影响实际访问。

登录起固定 1,800 秒到期，刷新、切入口和授权变化不会续期；会话在 MySQL 存储，浏览器使用 HttpOnly Cookie。退出、账号停用/锁定、密码重置会回收相应会话。

## 后续使用建议

维护账号先核实人员关联，再按职责建立角色并授予明确操作权限。演示账号优先使用合成数据或不关联员工，避免把真实员工资料绑定到共享测试身份。首检保持上述模型稳定，RBAC1/RBAC2 另按阶段扩展。
